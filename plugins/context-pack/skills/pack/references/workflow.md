# 작업별 Context Pack 절차

변경 요청을 받으면 AI가 작업에 필요한 맥락을 준비하고 그 기준으로 구현·검증한다.
사용자에게 문서 작성을 떠넘기지 않는다. 프로젝트의 지침·개인 규칙·현재 요청의 권한이 기준이다.
이 절차는 권한을 확대하거나 기존 승인·안전장치를 대체하지 않는다.

## 1. 작업을 구분한다

- 질문·비교·원인 설명·읽기 전용 리뷰는 답만 한다. 사용자가 팩·계획 산출물을 요청했을 때만 그것을 만든다.
- 사소하고 경계가 분명한 변경은 목표·파일 경계·규칙·검증·완료 조건을 채팅에 짧게 정리한다.
  파일 수만으로 크기를 정하지 않는다. 여러 계층, 중요한 데이터, 인계가 걸린 작업은 다섯 문서로 남긴다.
- 팩을 만드는 것과 구현하는 것은 별개다. 계획·팩만 요청받았다면 코드 변경을 시작하지 않는다.

## 2. 필요한 근거를 읽는다

이 폴더의 `project.md`가 있으면 지침 정본과 관련 스킬·결정 목차·검증 원본을 찾는 길잡이로 쓴다.
실제 파일과 현재 브랜치가 기준이다. 오래된 프로젝트 안내와 코드가 다르면 안내를 바로잡는다.

- 현재 사용자 변경과 진행 중인 계획을 확인한다. 기존 변경을 자신의 수정 범위에 포함시키지 않는다.
- 증상·기대 동작과 직접 이어지는 코드·테스트·관련 결정만 읽는다. 저장소 전체를 팩에 복사하지 않는다.
- 수정 대상 하위 디렉터리에 별도 지침이 있으면 함께 읽고 적용 범위를 따른다.
- 관찰한 사실은 파일·테스트·로그 근거로, 추측은 가설로 구분한다. 재현 전에 원인을 단정하지 않는다.
- 새 파일이 필요하면 그 목적과 위치를 정한다. 원인을 모르면 먼저 조사 범위를 정하고 조사 후 수정 범위를 확정한다.

## 3. 다섯 문서를 내용까지 작성한다

`context/<작업명>/`에 작성한다. 이 폴더의 `templates/`를 복사하거나 설치된 생성기를 사용할 수 있다.
빈 양식 생성만으로 준비됐다고 보고하지 않는다. 기존 팩·계획을 이어 쓰는 방법은 `integrations.md`를 따른다.
같은 작업이면 기존 팩을 갱신하고, 이름만 같은 다른 작업이면 새 이름을 쓴다. 두 세션이 같은 팩을 동시에 고치지 않는다.

| 문서 | 반드시 담을 판단 |
| --- | --- |
| `task.md` | 문제·기대 동작·이번에 하지 않을 일, 확인한 근거와 미확인 가설 |
| `files.md` | 먼저 읽을 파일, 수정·생성 허용 파일, 별도 허가가 필요한 영역과 이유 |
| `rules.md` | 이번 작업에 적용할 규칙과 원본 경로, 승인된 결정, 멈춰야 할 조건 |
| `tests.md` | 바뀔 동작을 검증하는 시나리오, 명령·실행 디렉터리·환경, 결과 파일·확인 한계 |
| `done.md` | 관찰 가능한 완료 조건, 검증·범위 대조, 결과 보고 기준 |

규칙 전체를 복사하지 말고 관련 항목과 원본 경로를 연결한다. 작업 중 새로 확인한 사실·결정·범위를 갱신한다.
계획을 장식하거나 테스트를 통과시키려고 기준을 낮추지 않는다. 범위 변경의 이유와 권한을 기록한다.

## 4. 그 경계 안에서 구현한다

팩 위치와 수정 계획을 짧게 알린 뒤 요청받은 작업을 수행한다. 팩 작성마다 별도 승인을 요구하지 않는다.
프로젝트가 계획 승인을 요구하면 따르되, 같은 내용으로 이미 받은 승인을 반복해서 묻지 않는다.

- 읽기 목록과 수정 허용 목록을 구별한다. 읽어 본 파일이라고 수정 권한이 생기지는 않는다.
- 허용 범위를 넘어야 하면 먼저 이유를 정리한다. 현재 요청에서 이미 허용한 범위 안의 보완은 팩을 갱신하고 진행한다.
  금지 영역·별도 승인 사항·요청 밖 동작 변경은 수정 전에 사용자 결정을 받는다. 팩을 스스로 고쳐 권한을 만들지 않는다.
- 공개 API·스키마·의존성·운영 설정·보안 경계 변경은 프로젝트 규칙과 현재 요청에 비춰 판단한다.
  원문의 특정 파일 개수 예시를 모든 프로젝트의 고정 승인 기준으로 만들지 않는다.
- 관련 없는 리팩터링·일괄 포맷·사용자 변경 되돌리기를 끼워 넣지 않는다.

## 5. 실제 결과로 검증한다

`tests.md`의 관련 검증부터 실행한다. 명령은 CI·기존 스크립트와 대조하고 환경·디렉터리를 확인한다.
명령이 정의돼 있다는 것, 실행했다는 것, 성공했다는 것을 구별한다. 도구·기기·권한이 없으면
실행하지 않은 이유와 남은 명령을 적는다. 실행하지 않고 성공을 예상해 보고하지 않는다.

테스트 실패는 실제 원인으로 분류한다. 기존 기능·운영 데이터·검증 단언을 약하게 만들어 가리지 않는다.
일치 여부를 확인한 뒤에는 새 변경·실패·미해결 위험이 있을 때만 검증을 더 넓히거나 반복한다.

마지막에 현재 작업의 diff(추적 안 된 새 파일도 포함)를 수정 허용 목록과 대조한다.
처음부터 있던 사용자 변경을 자신의 결과로 보고하지 않는다. 커밋·푸시·머지·배포 여부는 요청받은 범위만 따른다.

## 6. 완료를 판정하고 보고한다

`done.md` 조건을 하나씩 실제 코드·결과와 대조한다. 미완료를 숨기지 않는다.
프로젝트의 결과 보고 형식이 있으면 그 형식 안에 다음 정보를 담아 한 번만 보고한다.

- 바뀐 동작과 수정 파일
- 실행한 검증·결과 위치, 미실행 이유와 확인하지 못한 부분
- 남은 위험·미완료 조건
- 이번 작업에서 유지한 주요 경계(`Not Changed`)

지속되는 정책·설계 결정은 프로젝트의 기존 결정 문서에 남기고 팩에서는 경로를 연결한다.
리뷰·인계에 사용할 때는 관련 diff와 근거를 골라 전달한다. 토큰·개인정보·실데이터가 든 원본 로그는 넣지 않는다.
