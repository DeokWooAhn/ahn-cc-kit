# 프로젝트 지침 설계

루트 지침 한 장으로 모든 것을 담으려 하면 길어지고, 길어지면 안 읽힌다.
**어떤 작업이든 걸리는 규칙만 루트에 두고 나머지는 자리를 나눈다.** 그 자리를 정하는 것이 이 스킬이다.

작업별 맥락 정리(다섯 문서)는 그 구조 위에 얹는다. 구조가 없으면 팩부터 만들어도 기댈 데가 없다.

## 먼저 어느 경우인지 가른다

| 상황 | 할 일 |
| --- | --- |
| 지침이 없거나 몇 줄뿐이다 | 구조부터 설계한다. 아래 전부 |
| 지침은 있는데 한 파일에 다 들어 있다 | 자리를 나눈다. 조사 → 설계 → 이전 |
| 이미 자리가 나뉘어 있다 | **갈아엎지 않는다.** 빠진 절만 보완하고 팩을 연결한다 |

**기존 구조가 멀쩡하면 그대로 둔다.** 이미 돌아가는 지침을 템플릿 모양으로 바꾸는 것은
개선이 아니다. 무엇이 실제로 빠졌는지 말하고 사용자가 고르게 한다.

## 조사

1. 루트의 `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`를 읽는다. import·링크도 따라가 **실제 정본**을 찾는다.
   두 파일이 각각 독립적으로 길면 소유자가 다를 수 있다. 파일명만으로 정하지 않는다.
2. 이 저장소를 **누가 읽는지** 확인한다. 다른 에이전트, 리뷰 봇, CI가 같은 파일을 읽는지 본다.
   이것이 진입점 배치를 정한다 — [references/structure.md](references/structure.md)
3. 이미 있는 스킬·문서·결정 기록·작업 메모의 위치와 검증 명령·CI를 확인한다.
   도입에 필요한 경로만 본다. 앱 전체를 읽지 않는다.
4. 팀 공통 규칙인지 개인 설정인지 가른다. 개인 도입이면 팀 파일과 전역 설정을 고치지 않는다.
   개인 지침을 읽지 않는 도구에는 적용되지 않는다는 것을 알린다.

## 설계

[references/structure.md](references/structure.md)로 **무엇을 어디에 둘지** 정한다.
루트 지침·스킬·결정 기록·개인 파일 네 자리의 판별 기준과 진입점 선택이 있다.

[references/sections.md](references/sections.md)로 **루트 지침의 절**을 정한다.
절 차례, 절마다 답해야 할 질문, 자주 빠뜨리는 것, 골격이 있다.

정한 배치와 그 이유를 짧게 알리고 진행한다. 이미 받은 도입 권한으로 하되
프로젝트에 별도 승인 규칙이 있으면 따른다. **모든 작업마다 새 승인을 요구하는 규칙을 추가하지 않는다.**

## 작성

1. 루트 지침을 조사한 내용으로 채운다. 골격의 제목만 남기지 않는다.
   채울 내용이 없는 절은 뺀다. 플랫폼별 명령은 원본에 두고 경로로 가리킨다.
2. 자리를 나눠야 하는 내용은 옮긴다. 옮긴 자리에서 루트의 해당 줄은 경로 한 줄로 줄인다.
   **원본의 근거·불확실성·권한·갱신 규칙을 보존한다.** 요약하면서 조건을 지우지 않는다.
3. `## 세부 문서` 표를 만든다. 상황을 먼저 적고 파일 경로를 뒤에 적는다.
   스킬이 있으면 각 `SKILL.md`의 `description`에서 "언제 불리는지"를 읽어 상황 칸을 쓴다.
4. 작업별 팩을 함께 도입하면 생성기를 실행한다. `<plugin>`은 `skills/setup/`에서 두 단계 위다.

   ```bash
   python3 "<plugin>/scripts/context_pack.py" setup --project "<project>" --instructions AGENTS.md
   ```

   `--instructions`는 조사한 정본에 맞춰 고른다. 스크립트는 `.context-pack/`에 절차·안내·템플릿을 복사하고
   지침에 시작 규칙을 연결한다. 기존 파일은 덮어쓰지 않는다. 재실행은 설치 확인이며 자동 업그레이드가 아니다.
5. 생성기가 `CLAUDE.md` 브리지를 만들었으면 왜 그렇게 나눴는지 한 줄을 위에 더한다.
   `AGENTS.md` 쪽 브리지는 정본 판별에 쓰이므로 내용을 바꾸지 않는다 — [references/structure.md](references/structure.md)
6. `.context-pack/project.md`에 **설계 결정과 그 이유**를 적는다. 경로 목록이 아니라 왜 그렇게 나눴는지다.
   나중에 구조를 고칠 때 이 기록이 근거가 된다.
7. 기존 작업 시작 메모와 겹치는 루트 항목은 하나의 진입점으로 합친다.
   팀 지침과 개인 지침의 소유권을 넘기지 않는다. 다른 도구의 진입 파일이 정본을 읽는지도 확인한다.
8. [pack 스킬의 integrations.md](../pack/references/integrations.md)로 기존 계획·오케스트레이터·테스트·리뷰·guard와
   역할을 나눈다. 외부 kit에 동등한 절차가 있으면 그것을 정본으로 연결하고 같은 정책을 두 벌 만들지 않는다.

## 확인

- 루트 지침에서 각 자리를 경로로 찾아갈 수 있고, 그 경로가 실제로 존재하는지 확인한다.
- `## 세부 문서` 표의 모든 파일을 열어 본다. 없는 파일을 가리키는 표는 없는 것만 못하다.
- 팩을 도입했으면 임시 폴더에서 `new` 명령으로 다섯 문서를 생성해 본다.
  빈 템플릿 생성과 AI의 내용 작성을 구분해 보고한다.
- 다음 작업의 흐름을 설명한다: **근거 조사 → 맥락 정리 → 구현 → 검증 → 완료 기준 대조**.
  질문에는 팩을 만들지 않고, 사소한 변경은 같은 항목을 채팅으로 축약한다.
- 지침 기반 자동화이며 명령을 차단하는 보안 관문이 아님을 설명한다.
  플러그인 설치·도입을 이유로 커밋·푸시·배포·운영 접근 권한을 추가하지 않는다.

설계만 요청받았다면 여기서 끝낸다. 예시 작업을 명분으로 앱 코드나 CI를 바꾸지 않는다.
