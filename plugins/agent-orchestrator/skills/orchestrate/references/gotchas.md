# 함정

실제로 겪은 것만 적는다.

## `codex exec` 가 시작하자마자 멈춘다

로그가 `Reading additional input from stdin...` 한 줄에서 멈추고 더 자라지 않는다.
codex는 인자를 받아도 stdin을 한 번 확인하는데, EOF가 오지 않으면 거기서 기다린다.

```bash
codex exec -s workspace-write "$(cat 프롬프트)" < /dev/null > 로그 2>&1
```

`< /dev/null` 을 붙인다. 그리고 **프롬프트 파일 작성(heredoc)과 실행을 한 명령에 합치지 않는다.**
heredoc이 stdin을 쓴 뒤 같은 셸에서 codex를 실행하면 stdin이 닫히지 않은 채 넘어간다.
파일을 먼저 만들고, 실행은 따로 보낸다.

## 백그라운드로 보내면 멈춘 것을 모른다

위 증상은 프로세스가 살아 있는 채로 멈추므로 완료 알림이 오지 않는다.
한참 뒤 사람이 "왜 이렇게 오래 걸리냐"고 물어서야 알게 된다.

넘긴 뒤 몇 분 지나도 로그 크기가 그대로면 멈춘 것으로 본다.
정상이면 로그가 수십만 바이트로 자란다.

## `git status` 로는 untracked 파일 수정을 못 잡는다

구현자가 새로 만든 파일을 두 번째 왕복에서 고치면, 표시는 `??` 그대로다.
변경 전후를 `git status` 출력으로 비교하면 "아무것도 안 바뀜"으로 보인다.

`scope-guard.sh`는 내용 해시로 비교한다. 넘기기 **직전에** 스냅샷을 찍어야 한다.
Planner가 문서를 고친 뒤 스냅샷을 안 찍으면 그 변경이 구현자의 위반으로 잡힌다.

## 검증 명령은 돌려 보고 적는다

예: Android 라이브러리 모듈은 `./gradlew :모듈:test --tests "..."` 가 동작하지 않는다.
실제 테스트 태스크가 variant별(`testDebugUnitTest`)이고 `test`는 묶는 수명주기 태스크라 `--tests` 를 받지 않는다.
순수 JVM 모듈에서는 되므로, 한 모듈에서 되는 것을 보고 유추하면 틀린다.

## 구현자가 과하게 조심한다

범위를 좁게 주면 검증까지 건너뛴다.
"detekt는 자동 수정으로 다른 파일을 건드릴 수 있어서 실행하지 않았습니다" 같은 보고가 돌아온다.

계획의 검증 절에 **그 명령이 파일을 바꾸지 않는다**고 적어 준다.

## Claude Code 데스크탑: 자동 턴에서는 세션을 못 띄운다

백그라운드 작업 완료 알림으로 시작된 턴에서는 `start_session`이 거부된다.
제안 카드도 다른 폴더를 가리킬 수 없다.

구현을 백그라운드로 보내면 그 완료 턴에서 리뷰 세션을 바로 띄울 수 없다.
사람이 한 번 말을 걸어야 한다. 애초에 작업할 저장소 폴더에서 세션을 시작하면 덜 걸린다.
