# 변경 설명 페이지

리뷰가 "이 변경이 맞는가"를 판정한다면, 이 스킬은 "이 변경을 이해했는가"를 돕습니다.
결과는 한 장짜리 HTML 페이지입니다. 변경을 고치거나 평가하지 않습니다.

## 1. 대상 정하기

- 요청에 PR 번호·URL, 브랜치, 커밋 범위, "지금 작업 중인 변경"이 있으면 그것을 씁니다. 없으면 묻습니다.
- diff는 `gh pr diff <번호>`, `git diff <base>...<head>`, `git diff`와 `git diff --staged`로 얻습니다.
- diff만 읽지 않습니다. 바뀐 코드를 부르는 쪽과 바뀐 코드가 부르는 쪽, 관련 테스트와 문서까지 넓게 읽습니다.
  배경은 여기서 나옵니다.

## 2. 페이지 구성

이 순서로 한 페이지에 둡니다. 탭으로 나누지 않습니다.

1. **배경** — 두 단계로 씁니다.
   - 처음 보는 사람을 위한 넓은 배경: 이 시스템이 무엇을 하고 어떤 부분으로 이루어졌는지.
     아는 사람은 건너뛸 수 있게 접어 둡니다.
   - 이 변경을 읽는 데 바로 필요한 좁은 배경.
2. **직관** — 세부가 아니라 핵심 아이디어입니다. 작은 예시 데이터로 "바뀌기 전에는 이랬고 이제는 이렇다"를
   보여 줍니다. 그림을 아끼지 않습니다.
3. **코드** — 파일 순서가 아니라 이해하기 쉬운 순서로 변경을 묶어 훑습니다. 묶음마다 무엇을 왜 바꿨는지,
   핵심 코드 몇 줄, `파일:줄`을 둡니다.
4. **퀴즈** — 객관식 5문항입니다. 변경의 실체를 이해해야 풀 수 있는 중간 난이도로 내고, 말장난이나 함정은
   넣지 않습니다. 보기를 고르면 맞았는지와 이유를 바로 보여 줍니다. 오답 보기에도 왜 틀렸는지를 둡니다.

## 3. 글

- 대화에서 쓰는 언어로 씁니다.
- 고전적 문체(classic style)로 씁니다. 독자가 직접 보도록 사실을 보여 주는 명료한 문장이고,
  섹션과 섹션이 자연스럽게 이어집니다. Martin Kleppmann의 글이 좋은 본보기입니다.
- 핵심 개념과 정의, 놓치기 쉬운 경계 사례는 callout으로 뽑습니다.
- 코드와 diff에 없는 동작을 지어내지 않습니다. 확인하지 못한 것은 확인하지 못했다고 씁니다.
- 비밀값(키, 토큰, 비밀번호, 실제 서비스 ID)은 diff에 있어도 페이지에 옮기지 않습니다.

## 4. 그림

- 그림 종류를 2~3가지로 정해 페이지 전체에서 되풀이해 씁니다. 예를 들면 이렇습니다.
  - 사용자가 보는 화면을 단순하게 줄인 모형(UI 변경일 때)
  - 구성 요소 사이의 데이터 흐름. 예시 데이터를 반드시 넣습니다.
  - 변경 전후 비교
- ASCII 그림은 쓰지 않습니다. HTML·CSS 상자와 목록으로 그립니다.

## 5. 파일과 전달

- CSS와 JS를 모두 넣은 HTML 파일 하나로 만듭니다. 외부 스크립트·폰트·이미지 없이 열려야 합니다.
  형식 세부와 퀴즈 골격은 [references/html-format.md](references/html-format.md)에 있습니다.
- 저장소 밖에 저장합니다. `EXPLAIN_DIFF_DIR` 환경 변수가 있으면 그 폴더, 없으면 `~/explain-diff/`입니다.
  파일명은 오늘 날짜로 시작하는 `YYYY-MM-DD-<slug>.html`입니다. 시간순으로 정렬되고 버전 관리에 섞이지 않습니다.
- 저장하기 전에 references의 점검 목록을 하나씩 확인합니다.
- 이 세션에 비공개 페이지를 게시하는 도구(예: Artifact)가 있으면 같은 HTML을 비공개로 게시해 링크도 줍니다.
  공개 게시는 하지 않습니다. 도구가 없으면 파일 경로와 여는 명령(`open`, `xdg-open`)을 줍니다.
