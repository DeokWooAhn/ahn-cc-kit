# 화면 다듬기

AI가 만든 화면은 같은 방식으로 틀린다. 모든 면이 빛나고, 라벨마다 이모지가 붙고,
여백은 그때그때 다르고, 문구는 과장돼 있다. 제품 이름을 바꿔도 그대로 어울린다.

**고치는 것은 만듦새이고 제품은 그대로 둔다.** 기능도 내용도 절 순서도 유지한다.
바뀌는 것은 모든 크기·색·낱말·그림이 의도를 갖게 되는 것뿐이다.

## 원본은 unslop 이다

이 스킬은 Damir Sokolovsky 의 [unslop](https://github.com/heydamir/unslop)(CC BY 4.0)을
**대체하지 않는다.** 진단 목록, 방향 다섯 줄, 아홉 단계의 순서는 그쪽이 정본이다.
설치돼 있으면 그 절차를 따르고, 이 스킬은 그 위에 **보정**만 얹는다.

```bash
claude plugin marketplace add heydamir/unslop
```

```bash
claude plugin install unslop@heydamir
```

원본은 웹 대상이다(React·Tailwind·HTML·CSS). 모바일에서는 스냅샷 스크립트,
정적 HTML 재구성, 스토리 영상이 돌아가지 않고 토큰 값도 CSS 기준이다.
**안 맞는 것은 그 셋과 값뿐이고 판단 기준은 그대로 쓴다.**

원본이 없어도 이 스킬만으로 진행할 수 있다. 그때는 아래 순서를 그대로 따른다.

## 순서

1. **화면을 본다.** 코드만 읽지 않는다. 실제로 띄워 스크린샷을 찍는다 —
   [references/mobile.md](references/mobile.md)에 플랫폼별 방법이 있다
2. **진단한다.** 찾은 것마다 한 줄, 어디에 있는지 함께 적는다.
   **관찰과 해석을 가른다** — "모서리가 16이다"는 관찰이고 "그래서 목록 행과 입력창이
   한 덩어리로 보인다"는 해석이다
3. **얼마나 바꿀지 정한다.** 아래 "덜 바꾸는 쪽"을 읽는다
4. **방향 다섯 줄을 쓰고 멈춘다.** Product·Character·World·Moments·Signature.
   **사용자 답을 받기 전에 코드를 고치지 않는다.** 방향을 나중에 바꾸면 전부 다시 해야 한다
5. **아홉 단계로 고친다.** 간격 → 색 → 아이콘 → 문구 → 글자 → 배치 → 디테일 → 비주얼 → 모션.
   한 컴포넌트를 끝내고 넘어가지 않고 **같은 항목을 화면 전체에 적용**한다
6. **검수한다.** 다시 띄워 진단 목록과 대조한다
7. **보고한다.** 방향, 단계마다 바꾼 것, 확인한 것과 확인 못 한 것

## 덜 바꾸는 쪽

**이미 쓰이는 화면에서는 변화 자체가 비용이다.** 진단을 정직하게 읽고 범위를 정한다.

| 상태 | 할 일 |
| --- | --- |
| 징후가 색·글자·아이콘·문구에 걸쳐 많다 | 전체 절차 |
| 대체로 정돈돼 있고 몇 군데만 걸린다 | **다듬기 모드.** 진단에서 찾은 것만 고친다. 방향은 기존 브랜드에서 가져온다 |
| 걸리는 게 없다 | **그렇다고 말한다.** 작은 제안 두셋을 값과 함께 내고 거기서 멈춘다 |

**루트 지침에 이미 디자인 규칙이 적혀 있으면 다듬기 모드로 시작한다.**
테마 토큰만 쓰기, 색만으로 뜻을 전하지 않기, 문구 규칙 같은 것이 이미 있다면
그 프로젝트는 심한 슬롭이 아니다. 규칙을 먼저 읽고 무엇이 이미 막혀 있는지 확인한다.

**좋은 화면을 달라 보이게 하려고 바꾸지 않는다.**

## 값은 토큰에서 고친다

화면 파일의 숫자를 직접 바꾸지 않는다. 디자인 소스와 테마 토큰에서 고치고
화면은 토큰을 가리키게 한다 — [references/design-source.md](references/design-source.md)

새 색·새 글꼴·새 토큰을 만들기 전에 **같은 역할의 값이 이미 있는지** 본다.
공통 컴포넌트를 바꾸면 그것을 쓰는 다른 화면도 바뀐다. 바뀌는 화면을 함께 적는다.

## 한국어 화면

원본의 값은 영문 기준이다. 굵기·줄 높이·줄바꿈을 그대로 쓰면 한글에서 다르게 보인다.
[references/korean.md](references/korean.md)를 읽는다.

## 장식처럼 보여도 정보인 것

**효과를 지우기 전에 지웠을 때 사용자가 잃는 정보를 먼저 확인한다.**

상태를 알리는 점과 시선만 끄는 배지는 다르다. 선택된 행을 보여 주는 배경색과
모든 행을 제각각 강조하는 색은 다르다. 포커스 표시를 장식으로 오해해 지우면
키보드로 쓰던 사람이 길을 잃는다.

색을 줄일 때는 **그 색이 전하던 뜻을 먼저 적어 본다.** 같은 빨강이라도
오류·품절·삭제는 서로 다른 맥락이다.

## 하지 않는 것

- 방향 확인 없이 코드를 고치는 것
- 기능·데이터 흐름·API·상태 관리를 건드리는 것
- 정보 구조를 바꾸는 것 — 열을 숨기거나 상세로 옮기는 것은 **따로 판단받는다**
- 스크린샷 없이 "디자인이 좋아졌다"고 보고하는 것
- 이번 변경으로 지표가 좋아졌다고 말하는 것
