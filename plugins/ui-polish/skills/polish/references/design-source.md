# 디자인 소스와 토큰

**화면 파일의 숫자를 직접 고치지 않는다.** 값은 위에서 내려온다.

```text
디자인 소스  →  테마 토큰  →  화면
```

이 경로가 끊겨 있으면 다듬기는 한 화면에서만 맞고 다음 화면에서 다시 어긋난다.

## 먼저 확인할 것

1. **테마 토큰이 어디에 정의돼 있나** — 색·타이포그래피·간격·radius·모션
2. **화면이 토큰을 쓰고 있나** — 직접 쓴 값이 섞여 있으면 그 자체가 진단 항목이다
3. **디자인 소스가 있나** — `.pen` 파일, 디자인 도구 링크, 스펙 문서

세 번째가 없어도 진행할 수 있다. 다만 **고친 값이 어디에 기록되는지**는 정해 둔다.
토큰만 고치고 디자인 소스를 그대로 두면 다음에 디자인을 받을 때 또 어긋난다.

## pencil(`.pen`)을 쓸 때

pen.dev 데스크톱 앱이 **실행 중이어야** MCP 도구가 붙는다. 꺼져 있으면 연결이 실패한다.

- 앱이 꺼져 있으면 **건너뛰고 건너뛰었다고 보고한다.** 사용자에게 켜 달라고 할 수는 있지만
  답을 기다리느라 나머지 작업을 멈추지 않는다
- `.pen` 파일은 암호화돼 있다. **일반 파일 읽기 도구로 열지 않는다.** MCP 도구로만 다룬다
- 디자인 소스에서 값을 바꿨으면 **토큰에도 반영한다.** 둘이 갈라지면 어느 쪽이 정본인지 모른다

## 값을 바꿀 때

**같은 역할의 값이 이미 있는지 먼저 본다.** 새 토큰을 만들기 전에 기존 것으로
해결되지 않는 이유를 댈 수 있어야 한다.

공통 컴포넌트를 고치면 **그것을 쓰는 다른 화면도 바뀐다.**
한 화면이 답답해 보여서 공통 버튼 높이를 줄이면 다른 화면의 긴 라벨이 잘릴 수 있다.

바꾸기 전에 가른다.

| 어느 쪽인가 | 어떻게 |
| --- | --- |
| 공통 규칙이 틀렸다 | 토큰·공통 컴포넌트를 고치고 **영향받는 화면을 모두 적는다** |
| 이 화면만의 사정이다 | 그 화면에서 해결한다. 공통 정의에 예외 조건을 늘리지 않는다 |

바꾼 범위를 따라 검수 범위도 넓어진다. 공통 입력창의 포커스 표시를 바꿨으면
검색창뿐 아니라 로그인·설정 폼에서도 확인한다.

## ui-contract 와의 관계

디자인이 **있고** 그대로 구현해야 하면 `ui-contract`의 일이다 — 수치를 계약으로 고정하고
그 계약만 보고 구현한다.

이 스킬은 **이미 만든 화면**을 다듬는다. 둘은 이어진다.

```text
디자인을 만든다        →  ui-contract 로 계약을 뽑아 구현한다  →  다듬는다
(pencil 또는 디자이너)     (수치가 틀리지 않게)                    (제품다워지게)
```

계약이 있는 화면을 다듬을 때는 **계약을 먼저 읽는다.**
계약에 적힌 값을 바꾸려면 그것은 다듬기가 아니라 디자인 변경이므로 따로 판단받는다.
