# 검증과 리뷰 기준

## 통과 조건

- 빌드가 통과한다
- `layout-contract.json`의 값이 코드에 그대로 반영됐다
- 폰트·색·shadow가 `design-tokens.json`의 `codeRef`가 가리키는 코드 토큰으로 들어갔다
- 허용 파일 밖이 바뀌지 않았다
- 새 디자인 토큰·새 색상·새 폰트·새 컴포넌트가 생기지 않았다
- 새 의존성이 추가되지 않았다
- 기준 상태의 스크린샷을 남겼다

**빌드 통과는 UI 작업의 완료가 아니다.** 컴파일되는 틀린 UI는 흔하다.

## 허용 오차

목표는 pixel perfect가 아니라 계약 일치다. 그래서 오차의 종류를 가른다.

| 항목 | 기준 |
| --- | --- |
| 위치·크기 | 기준 디바이스에서 2pt / 2dp 이내 |
| 텍스트 렌더링 | 플랫폼 폰트 렌더링 차이는 허용. 단 **크기·굵기·줄 수는 허용하지 않는다** |
| 색 | 기존 토큰을 썼으면 통과. 값이 비슷한 다른 색은 불통과 |
| shadow | 계약이 가리키는 토큰과 같아야 한다. 정확히 맞는 토큰이 없었다면 **승인을 받아 계약에 적힌** 대체 토큰만 통과. 구현자가 고른 "가장 가까운 것"과 새로 만든 토큰은 불통과 |
| line-height | 플랫폼 처리 차이로 인한 첫 줄 여백 차이는 허용 |

**"비슷해 보인다"는 통과 사유가 아니다.** 통과 사유는 "계약 값과 같다" 또는
"허용된 플랫폼 차이다" 둘뿐이다.

## 스크린샷

렌더링 결과는 Preview·UI 테스트·스크린샷 테스트 중 프로젝트에 이미 있는 방법으로 남긴다.
없으면 **스크린샷 체계를 새로 만들지 말고** 그 사실을 보고한다.

적어도 이 상태는 남긴다. 디자인에 해당 상태가 정의돼 있을 때만이다.

- 기준 상태(디자인이 보여 주는 그 화면)
- 다크 모드
- 가장 긴 텍스트·가장 큰 숫자
- 빈 상태, 오류 상태

**스크린샷 없이 "디자인과 일치한다"고 쓰지 않는다.**
확인한 상태와 확인 못 한 상태를 나눠 적는다.

CI에서 스크린샷 비교를 돌리는 체계가 이미 있으면 거기에 붙인다.
없는 프로젝트에 도입하는 것은 이 작업의 범위가 아니다.

## 화면을 못 봤을 때

**못 띄운 것과 틀린 것은 다른 문제다.** 섞으면 멀쩡한 코드를 고치게 된다.

| 무엇인가 | 이런 모습이다 | 할 일 |
| --- | --- | --- |
| 환경 문제 | 기기·시뮬레이터가 없다, 런타임이 빠졌다, 빌드 도구가 안 선다, 시간이 초과됐다 | **화면 코드를 고치지 않는다.** 못 봤다고 적고 나머지를 진행한다 |
| 준비 문제 | 미리보기에 넘길 값이 없다, 의존성이 주입되지 않는다, 더미 데이터가 없다 | 미리보기·테스트 쪽을 고친다. 화면 코드는 건드리지 않는다 |
| 화면 문제 | 띄웠는데 계약과 다르다 | **이것만 UI 수정 대상이다** |

가르는 질문은 하나다 — **화면 코드를 한 줄도 안 고쳐도 같은 실패가 나는가.**
그렇다면 UI 문제가 아니다.

못 본 항목은 **"불통과"가 아니라 "미확인"이다.**
확인하지 못한 것을 실패로 적으면 다음 사람이 있지도 않은 문제를 찾는다.
반대로 미확인을 통과로 적으면 아무도 그 자리를 다시 보지 않는다.

환경 문제는 **고치려 들지 말고 보고한다.** 기기를 붙이거나 런타임을 받는 것은
이 작업의 범위가 아니고, 그러다 보면 정작 요청받은 화면은 손도 못 댄 채 시간이 간다.

## 사람이 봐야 할 것

자동 검증이 못 잡는 자리다. 리뷰 요청할 때 이 목록을 함께 준다.

- 요소 사이 정렬(아이콘과 텍스트의 광학적 중심은 수치로 안 잡힌다)
- 강조 위계 — 합계·가격·제목이 디자인만큼 두드러지는가
- 긴 텍스트의 줄바꿈 위치
- 다크 모드에서 대비
- 터치 영역이 시각 크기보다 작아지지 않았는가
- 빈 상태·로딩 상태가 레이아웃을 흔들지 않는가

## 리뷰 입력

리뷰어에게 주는 것은 이것뿐이다.

- `layout-contract.json`, `design-tokens.json`, `component-map.md`, `ambiguity-report.md`
- diff
- 렌더링 스크린샷과 디자인 참조 이미지
- 이 문서의 경로

**구현자의 결론을 넣지 않는다.** "수치 다 맞췄습니다"가 입력에 들어가면
리뷰어는 그것을 확인하는 사람이 되지 판단하는 사람이 되지 않는다.

## 리뷰 출력

```markdown
## 판정
pass / needs_changes / blocked

## 불일치
| 파일:줄 | 항목 | 계약 | 실제 | 심각도 |

## 고쳐야 할 것
<!-- 파일과 함께. 지적마다 계약의 어느 줄을 근거로 하는지 적는다. -->

## 사람이 판단할 것
<!-- 계약에 없어서 리뷰어도 못 정하는 것. ambiguity-report로 돌아간다. -->

## 확인하지 못한 것
<!-- 못 본 상태와 그 이유. 없으면 "없음". 비워 두지 않는다. -->
```

**화면을 못 보고 내린 판정에는 그 사실을 함께 적는다.**
코드만 읽고 내린 `pass` 와 띄워 보고 내린 `pass` 는 같은 말이 아니다.

심각도는 셋이다.

- **blocker** — 계약 값과 다르다. 수정 전에는 넘어가지 않는다
- **major** — 허용 오차를 넘었거나 매핑되지 않은 컴포넌트를 새로 만들었다
- **minor** — 오차 안이지만 알아 둘 것. 고칠지는 사람이 정한다

판정이 `needs_changes`면 **지적된 항목만** 고친다.
리뷰를 핑계로 다른 자리를 같이 고치면 범위가 무너지고, 다음 리뷰가 무엇을 봐야 하는지 흐려진다.

판정이 `blocked`면 코드 문제가 아니라 계약이나 디자인 결정이 빠진 것이다.
구현을 계속하지 말고 `ambiguity-report.md`로 돌아간다.
