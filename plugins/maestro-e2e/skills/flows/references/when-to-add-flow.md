# Flow를 만들지 정하기

새 화면이나 기능이 생겼다고 Flow가 꼭 필요한 건 아니다. `smoke`는 PR마다 돌고 릴리스를 막으므로, 늘릴수록
CI 시간과 흔들림이 커진다. 아래 순서로 판단하고, 판단과 이유를 붙여 사용자에게 묻는다.

## 판단 순서

1. **이 화면이 깨지면 사용자가 앱의 핵심을 못 쓰나?** 아니면 대부분 만들지 않는다.
2. **새 Flow가 필요한가, 기존 Flow에 단계 하나로 되나?** 새 탭·메뉴처럼 열리는지만 보면 되는 화면은 기존 탭 이동
   smoke에 "열리고 기준점이 보인다" 한 단계를 넣는 쪽이 낫다. Flow 수가 늘지 않는다.
3. **서버가 필요한가?** 필요 없으면 `smoke`, 필요하면 `release`.

## 만드는 게 좋은 경우

| 경우 | 예 | 어떻게 |
| --- | --- | --- |
| 핵심 사용자 흐름에 있는 화면 | 앱의 주 기능 화면, 메인 목록 | 서버가 필요 없으면 `smoke`, 필요하면 `release` |
| 여러 화면을 잇는 진입점 | 새 탭, 하단 메뉴 | 기존 탭 이동 smoke에 단계 추가 |
| 전에 깨진 적 있거나 자주 바뀌는 곳 | 회귀가 났던 선택 창 | 그 회귀를 재현하는 단계 |
| 플랫폼마다 동작이 갈리는 곳 | 시트·대화상자 닫기 | 두 플랫폼 공통 Flow에 `when: { platform }`으로 |

## 안 만들어도 되는 경우

| 경우 | 이유와 대신할 것 |
| --- | --- |
| 정적 화면(약관, 라이선스, 앱 정보) | 열리는지만 보면 된다. 기존 탭 이동 smoke에 단계 하나면 충분하다 |
| 로직의 경우의 수가 핵심인 화면 | 유닛·ViewModel 테스트가 빠르고 안정적이다. E2E는 결과 하나가 화면에 보이는지만 본다 |
| 곧 사라질 화면(이벤트, 프로모션) | 만드는 비용이 쓰는 기간보다 크다 |
| 자동화하면 안 되거나 못 하는 흐름(결제, 본인인증, 실제 광고, 카메라, OS 설정, 외부 웹뷰) | 운영 데이터와 광고에 영향을 주거나 안정적으로 조작할 수 없다. 저장소 문서의 수동 확인 절차로 둔다 |
| 디자인만 바뀐 경우 | Maestro는 요소가 있는지를 보지 레이아웃 어긋남을 잘 못 잡는다. 스크린샷 테스트 영역이다 |
| 테스트 모드가 일부러 꺼 둔 화면(온보딩, 팝업 공지) | 기본 Flow에서는 뜨지 않게 해 둔 것이다. 확인하려면 그 화면만 켜는 실행 인자가 따로 필요하니, 그만한 가치가 있을 때만 만든다 |

## 묻는 방식

"만들까요?"만 묻지 않는다. 권하는 방법(새 Flow / 기존 Flow에 단계 추가 / 만들지 않음), 태그, 이유를 한두 줄로 붙인다.

> 새 화면 `설정 > 알림`: 토글만 있는 화면이라 새 Flow는 필요 없습니다. 탭 이동 smoke에 "열리고 `screen.notification`이
> 보인다" 한 단계만 추가하길 권합니다. 추가할까요?
